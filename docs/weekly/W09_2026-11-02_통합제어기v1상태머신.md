제어 모드 4종 + **생활 모드 4종(전역 목표값 세트)** + 상태 머신을 구현하고, **시나리오 17개가 요구하는 제약 충돌 해소 규칙**을

### T9.3 충돌 해소 알고리즘

```text
1. 각 정책(안전/절전/온도/습도/조도)이 원하는 액추에이터 명령을 제안한다
2. 제약 필터를 통과시킨다
     - 우천        → 창문 개방 금지
     - 끼임 감지    → 창문 이동 금지
     - 수면 모드    → 팬 RPM 상한 600 (모드 테이블에서 조회)
     - 미세먼지 등급 → 창문 개방률·팬 RPM 상한 (등급형)
     - 고온        → 조명 밝기 상한 60 %
3. 제약으로 막힌 정책은 "대체 수단"을 요청한다
     예) 창문이 막힘 → 온도 정책이 팬에 추가 부하를 요청
4. 동일 액추에이터에 복수 요청이 오면 priority가 작은 쪽이 최종 명령
5. 모든 대체 수단이 소진되면 feasibility = INFEASIBLE
```

> **이것이 발표의 핵심 차별점 ①을 구현하는 코드다.** 시나리오 C1에서
> *"창문이 막히니 팬이 역할을 전면 인수한다"* 는 동작이 바로 3단계에서 나온다.

## 5. 리스크 / 대응
| 리스크 | 대응 |
|---|---|
| 규칙 충돌(조도 규칙이 온도 규칙 덮어씀) | 우선순위 단일 진입점으로 출력 결정, 규칙별 우선순위 번호 명시 |
| **충돌 해소 로직이 과복잡해져 디버깅 불가** | 제안→필터→재분배→중재의 **4단계를 코드 구조로 그대로 반영**. 각 단계 결과를 로그로 남겨 추적 가능하게 한다 |
| **대체 수단 요청이 순환 참조** | 재분배는 **1회만** 허용. 2회차에도 해결 안 되면 INFEASIBLE로 넘긴다 |
| 상태 전이 무한 반복 | 전이 로그 기록, 최소 유지시간 도입(W10에서 히스테리시스로 정식 해결) |
| **하네스 골격이 뒤로 밀림** | W10 최대 리스크다. 이번 주에 **완성이 아니라 착수**만이라도 반드시 한다 |
