## 1. 재실 판단 — 센서 하나가 아니라 신호 셋

### 1.0 문 열림 센서 — "재실 상태는 문이 열릴 때만 바뀐다" (v3.2 · 호텔 객실 로직) ✅ 채택 (2026-10-05)

> **근거:** 호텔 객실 에너지 관리 시스템의 표준 로직. *"문이 열렸다 닫힌 직후 방 안에서 사람 신호가 있으면, 다음에 문이 열릴 때까지 재실로 본다.
> 신호가 없으면 다음에 문이 열릴 때까지 빈방으로 본다."* 잠든 투숙객 때문에 냉방이 꺼지는 오류를 막는 용도로 쓰인다.
> 원룸은 **출입구가 현관문 하나**뿐이라(가정 A19) 이 논리가 그대로 성립한다.

#### 구성

| 항목 | 내용 |
|---|---|
| 부품 | **리드 스위치 문 열림 센서** (유선 · MC-38형) — 현관문 상단, MCU GPIO 직결 · ~1,500원 (추정) |
| 대안 | 디지털 도어락이 열림 이벤트를 내보내면 센서 없이 도어락 이벤트로 대체 |
| Isaac Sim | `entrance_door` 를 Revolute Joint로 두고 **개방 각도 > 5° = 열림** (v2.1의 PIR 출입선 트리거 볼륨 자리 재사용) |

#### 판정 상태 4가지

```text
           문 열림                      문 닫힘
[재실 고정] ──────► [문 열림 중] ──────► [판정 창 3분] ──┬─ 사람 증거 있음 ─► [재실 고정]  (다음 문 열림까지)
[빈방 고정] ──────►        │                             └─ 사람 증거 없음 ─► [빈방 고정]  (다음 문 열림까지)
                           └─ 10분 넘게 열려 있음 ──────────────────────────► [폴백: 24시간 융합]

사람 증거 (판정 창 안에서 하나라도) = mmWave 이동/정지 신호 · 사람이 켜는 기기 전력 변화 · 리모컨·스위치 직접 조작
※ 휴대폰 Wi-Fi는 판정 창 증거로 쓰지 않는다 — 휴대폰을 두고 나간 경우를 걸러내기 위해서
```

| 상태 | 의미 | 이 상태에서의 동작 |
|---|---|---|
| **재실 고정** | 문이 닫힌 뒤 사람이 확인됨 | **시간 기준 없음.** 자도, 가만히 있어도, Wi-Fi가 끊겨도 재실 유지 |
| **빈방 고정** | 문이 닫힌 뒤 사람이 없었음 | 즉시 외출/절전. mmWave 단독 신호(커튼 · 옆집)는 무시 |
| 판정 창 | 문이 닫힌 직후 3분 | 사람 증거를 모은다 |
| **폴백** | 문 센서 고장 의심 · 문을 10분 넘게 열어 둠 | v3.1 24시간 융합 규칙(§1.2, 15분 기준)으로 자동 전환 |

#### 시간 기준은 어떻게 바뀌나

| | v3.1 (문 센서 없음) | **v3.2 (문 센서)** |
|---|---|---|
| 외출 확정 | 세 신호 모두 없음 **15분** | 문이 닫힌 뒤 **판정 창 3분** |
| 재실 유지 | 신호가 계속 이어져야 함 (Wi-Fi 증거 30분 유효 등) | **다음 문 열림까지 무조건 유지 — 시간 기준 없음** |
| 귀가 감지 | Wi-Fi 접속 (5–60 s 지연) | **문 열림 즉시** — 들어오는 순간 조명 |
| 남는 시간 값 | 15분 · 30분 · 60 s | **판정 창 3분 · 문 열어 둠 10분** (폴백 시에만 15분) |

> **"15분 같은 긴 대기 시간"은 정상 동작에서 사라진다.** 남는 것은 *문이 닫힌 직후 사람을 확인하는 짧은 창(3분)* 하나다.
> 이것은 "얼마나 오래 신호가 없어야 외출인가"라는 **추측**이 아니라, "방금 문이 닫혔을 때 안에 사람이 있었나"라는 **확인**이다.

#### 오판 상황이 원리적으로 사라진다

| 상황 | v3.1 (융합) | **v3.2 (문 기반)** |
|---|---|---|
| 휴대폰 절전으로 Wi-Fi 끊김 | 30분 내 증거로 버팀 | **문이 안 열렸으므로 재실 — 판단할 필요 없음** |
| 조용히 독서 · 수면 | mmWave 정지 신호로 유지 | **문이 안 열렸으므로 재실** |
| 휴대폰 두고 외출 | 15분 뒤 외출 | **문 닫힘 후 3분 안에 사람 증거 없음 → 외출** (Wi-Fi는 증거에서 제외) |
| 빈집 커튼 흔들림 · 옆집 | Wi-Fi · 전력 없음으로 기각 | **빈방 고정 상태라 무시** |
| 택배 받으러 문만 열었다 닫음 | – | 판정 창에서 mmWave가 사람 확인 → 재실 유지 |
| 손님만 나가고 나는 남음 | – | 판정 창에서 사람 확인 → 재실 유지 |

#### mmWave는 계속 켜 두되, 역할이 바뀐다

문 센서가 있으면 재실 판정에 mmWave가 필요한 시간은 **판정 창 3분**뿐이다. 그러나 mmWave를 끄지는 않는다.

| mmWave 역할 | v3.1 | **v3.2** |
|---|---|---|
| 재실 / 부재 판정 | 24시간 핵심 입력 | **판정 창(3분)에서만** |
| **책상 / 침대 위치 → AUTO 모드** | ✅ | ✅ 계속 필요 — 문 센서는 위치를 모른다 |
| **수면 판단** | ✅ | ✅ 계속 필요 |
| **문 센서 고장 감지** | – | ✅ **빈방 고정인데 강한 사람 신호가 이어짐 = 모순** |

- **끄지 않는 이유:** LD2410의 소비전력은 약 0.4 W(5 V · 80 mA 수준)로 1년 내내 켜도 약 3.5 kWh다. **끄는 이득이 거의 없고**, 위치 · 수면 · 고장 감지를 잃는다.
- **빈방 고정 상태에서는 읽는 주기만 낮춘다**(1 Hz → 0.1 Hz). mmWave는 이때 재실 판정이 아니라 **문 센서 감시용**이다.

#### 판정 창의 증거 강도 — 외출 직후 옆집 오검출 막기 (v1.3)

문 기반 판정에서 mmWave 오검출이 문제가 되는 순간은 **판정 창 3분**뿐이다. 가장 위험한 경우는
*"내가 나간 직후 옆집 사람이 벽 근처에 가만히 있는"* 상황이다. 이것을 재실로 판정하면 **다음 문 열림까지 냉방이 켜진 채 남는다.**
그래서 판정 창의 증거를 강도로 나눈다.

| 증거 | 강도 | 이유 |
|---|:---:|---|
| **방 안쪽 구간**(벽에 붙은 마지막 구간 제외)의 **움직임 신호** | **강** | 막 들어온 사람은 방 안을 걸어 다닌다 |
| 방 안쪽 구간의 정지 신호가 **60 s 이상 지속** | **강** | 앉거나 누운 사람 |
| **사람이 켜는 기기 전력 변화 · 리모컨/스위치 직접 조작** | **강** | 옆집 사람은 우리 기기를 켤 수 없다 |
| **벽에 붙은 구간**의 정지 신호 | 약 | 우리 침대일 수도, 벽 너머 옆집일 수도 있다 |
| 벽에 붙은 구간의 움직임 신호 | 약 | 벽 너머 이동과 구분이 어렵다 |

```text
판정 창 (문 닫힘 후 3분)
  강한 증거 1개 이상          → 재실 고정
  약한 증거만 있음            → 판정 창을 최대 10분까지 연장해 강한 증거를 기다림
       ├ 강한 증거 등장       → 재실 고정
       └ 휴대폰 Wi-Fi 해제 또는 연장 종료 → 빈방 고정
  아무 증거 없음              → 빈방 고정
```

> **휴대폰 Wi-Fi는 여전히 "재실 증거"로 쓰지 않는다.** 다만 판정 창 안에서 Wi-Fi가 **끊기는 것은 "외출" 쪽 증거**로 쓴다.
> 들어오는 사람은 거의 항상 방 안쪽을 걸어 다니므로, 이 규칙 때문에 귀가가 늦게 판정되는 경우는 드물다.

#### mmWave 자동 보정 — 사용자는 숫자를 넣지 않는다 (v1.3)

LD2410은 감지 범위를 **0.75 m 구간 9개(0–8번, 최대 약 6 m)** 로 나눈다. 오검출을 거르는 설정은
**① 몇 번 구간까지 볼지(감지 거리)** 와 **② 구간별 감도** 두 가지이며, **방 크기 · 센서 위치 · 벽 너머 상황에 따라 다르다.**
이를 사용자가 직접 넣지 않도록 두 단계로 자동 보정한다.

| 단계 | 언제 | 무엇을 | 방법 |
|---|---|---|---|
| **① 걷기 보정** | 설치할 때 1회 · 가구 재배치 후 | **감지 거리 상한** | *"센서에서 방 끝까지 한 번 걸어가 주세요"* → 움직임이 마지막으로 잡힌 구간 = 방 끝 → 그 구간까지만 본다. 레이더는 정지한 벽을 직접 재지 못하지만 걷는 사람은 확실히 잡는다 |
| **② 빈방 보정** | **빈방 고정이 2시간 이상 이어질 때마다** | **구간별 감도** | 빈방 동안 구간별 움직임 / 정지 신호 세기를 기록 → 최근 6회(낮 · 밤 섞어서)의 **상위 1 % 값 + 여유값**을 그 구간의 기준선으로 쓴다 |

- **문 센서가 있어서 가능한 보정이다.** "문이 닫힌 뒤 사람이 없다고 확정된 시간"은 확실한 빈방이므로, 그동안의 신호는 *사람이 아닌 것*(옆집 · 커튼 · 가구)으로 학습할 수 있다.
- **옆집 사람이 늘 집에 있지는 않으므로** 한 번이 아니라 여러 시간대의 기록을 모은다. 최소 2회가 쌓이기 전에는 기본값을 쓴다.
- 기본값(걷기 보정 전): 방 깊이 설정(`room_depth_m`)으로 계산 — 우리 원룸 5.25 m → **6번 구간까지**.

**보정이 망가지지 않게 하는 안전장치**

| 위험 | 대책 |
|---|---|
| 빈방으로 잘못 판정된 시간에 실제로 사람이 있었다 | 방 안쪽 구간 신호가 높은 기록은 **버린다** |
| 감도가 계속 올라가 우리 침대의 사람까지 못 잡게 된다 | 한 번에 바꾸는 폭 ±15 · **침대 · 책상 구간은 상한(60)을 넘기지 않는다** |
| 판정 창과 수면 판단은 필요한 민감도가 다르다 | **보정값은 센서에 쓰지 않고 소프트웨어 임계값으로 적용**한다. 원시 구간 신호는 그대로 받고, 판정 창은 보수적으로 · 수면 판단은 민감하게 따로 쓴다 |

#### 문 센서 고장 · 예외 → 24시간 융합으로 자동 폴백

| 감지 방법 | 판단 |
|---|---|
| **빈방 고정인데** mmWave 이동 신호 + 사람이 켜는 기기 조작이 함께 나타남 | 문을 거치지 않고는 들어올 수 없다 → **문 센서 이상 의심** |
| 휴대폰 Wi-Fi 접속/해제가 여러 번 있었는데 문 이벤트가 하루 넘게 없음 | 문 센서 신호 두절 의심 |
| 문이 10분 넘게 열려 있음 (환기 · 이사) | 문 기반 판정 불가 |
| → **폴백** | §1.2의 24시간 융합(mmWave + Wi-Fi + 전력, 15분 기준)으로 전환 · 사용자 알림 · 문 센서가 정상 이벤트를 다시 내면 복귀 |

> **문 센서 하나에 모든 것을 걸지 않는다.** 정상일 때는 문 센서가 판단을 단순하게 만들고, 고장이 나면 v3.1 융합이 그대로 받친다.
> 피드백 ①의 *"하나의 센서로만 판단하지 말라"* 와도 맞다 — 문 센서는 **언제 판단할지**를 정하고, **사람이 있는지**는 여전히 다른 신호가 확인한다.

| 유지 | mmWave | mmWave (변경 없음) |
| 오검출 기각 | PIR 미검출이면 mmWave 단독 신호 기각 | **Wi-Fi 미접속 + 가전 활동 없음**이면 mmWave 단독 신호 기각 |
| 외출 확정 | 양쪽 클리어 60 s (절전) / 30분 (외출) | **Wi-Fi 해제 + mmWave 클리어 + 가전 활동 없음 15분** |
| 부품 | PIR 2,200 + mmWave 11,900 | **mmWave 11,900** (Wi-Fi는 공유기 — 0원) |

**PIR을 뺀 이유:** PIR의 역할은 *"mmWave가 커튼 · 옆방을 사람으로 착각하는 것을 걸러내는 교차 검증"* 이었다.
같은 역할을 **휴대폰 Wi-Fi와 가전 전력**이 더 잘한다 — 둘 다 *"이 집 거주자가 지금 여기 있다"* 는 신호이고, 옆방 사람이나 커튼은 Wi-Fi에 접속하지도 쿡탑을 켜지도 않는다.

**mmWave를 남긴 이유:** Wi-Fi · 소리 · 전력은 모두 **사람이 무언가를 할 때만** 나온다. 자거나 조용히 책을 읽는 사람은
Wi-Fi 절전으로 끊기고, 소리도 전력 변화도 없다. **가만히 있는 사람을 직접 보는 신호는 mmWave뿐**이다(§1.3).
또 mmWave 거리 게이트만이 **책상 / 침대 영역**을 구분해 AUTO 모드를 고를 수 있다.

### 1.2 융합 규칙 — 하나라도 확실하면 재실, 셋 다 없을 때만 부재

> **v3.2부터 이 규칙은 폴백이다.** 정상일 때는 §1.0 문 기반 판정이 쓰이고, 문 센서 고장 · 문을 열어 둔 경우에만 이 규칙으로 돌아온다.

```text
evidence_wifi   = 휴대폰 MAC 접속 중                                    (강한 증거 · 소유자 식별)
evidence_mmwave = 이동 신호 OR 정지 신호(호흡 미세동작) 지속             (강한 증거 · 위치)
evidence_power  = 쿡탑 · PC · 세탁기 등 '사람이 켜는' 기기 전력 변화     (강한 증거 · 활동)

재실   = evidence_wifi OR evidence_power OR (evidence_mmwave AND 최근 30분 내 wifi/power 증거)
외출   = NOT 셋 다, 15분 지속                     (수면 모드에서는 외출 판정 금지)
기각   = mmWave 단독 + Wi-Fi 미접속 + 전력 활동 없음 → 커튼 · 옆방 · 반려동물로 간주
```

| 상황 | Wi-Fi | mmWave | 전력 | 판정 | 단일 신호였다면 |
|---|:---:|:---:|:---:|---|---|
| 귀가 | ✅ (현관 앞부터) | ✅ | – | **재실** | – |
| 조용히 독서 | ✅ | ✅ 정지 | – | **재실** | 소리만 보면 빈집 |
| 휴대폰 절전으로 Wi-Fi 끊김 | ✗ | ✅ | – | **재실** (30분 내 증거 있음) | Wi-Fi만 보면 외출 |
| 요리 중 휴대폰 방전 | ✗ | ✅ | ✅ 쿡탑 | **재실** | Wi-Fi만 보면 외출 |
| **휴대폰 두고 외출** | ✅ | ✗ 15분 | ✗ | **외출** (Wi-Fi 단독은 30분 후 무효) | Wi-Fi만 보면 계속 재실 → 낭비 |
| 커튼 흔들림 (빈집) | ✗ | ✅ | ✗ | **기각** | mmWave만 보면 재실 |
| 수면 중 Wi-Fi 끊김 | ✗ | ✅ 정지 | ✗ | **재실** (수면 모드 유지) | Wi-Fi만 보면 외출 |

> **조합이 단일 신호보다 나은 지점이 표의 마지막 열이다.** 팀원 안(Wi-Fi + 소리 + 전력)은 *"휴대폰을 두고 나가면 집에 있음으로 남는다"*
> 를 허용 오차로 두었지만, mmWave를 남기면 이 경우도 잡는다.

### 1.3 피드백 ② — "사람이 내는 주파수"로 재실을 판단할 수 있는가

**사람이 만드는 신호를 주파수로 정리하면 두 종류다.**

| 종류 | 신호 | 주파수 대역 | 언제 나오나 | 재실 판단 가치 |
|---|---|---|---|---|
| **음향 (공기 진동)** | 말소리 기본음 | 남 약 85–180 Hz · 여 약 165–255 Hz | 말할 때 | 활동 증거 |
| | 말소리 에너지 | 약 300–3,400 Hz (전화 대역) | 말할 때 | 활동 증거 · **사생활 위험** |
| | 발걸음 · 문 · 설거지 | 수십 Hz–수 kHz 광대역 충격음 | 움직일 때 | 활동 증거 |
| | 물소리 · 튀김 · 청소기 | 대역별 고유 모양 (FFT · 멜 스펙트로그램으로 구분) | 행동할 때 | **행동 분류에 유효** |
| | 호흡음 | 매우 작음 (근거리에서만) | 항상 | ❌ 원거리 마이크로 검출 불가 |
| **생체 미세동작 (전파 반사)** | **호흡** | **0.2–0.33 Hz** (분당 12–20회) | **항상 — 자는 중에도** | ✅ **존재의 증거** |
| | 심박 | 약 1.0–1.7 Hz (분당 60–100회) | 항상 | ✅ (60 GHz 바이탈 레이더) |

**결론**

1. **소리는 '활동'의 증거이지 '존재'의 증거가 아니다.** 조용히 있는 사람은 소리를 내지 않는다. 따라서 소리로는 *"있다"* 는 말할 수 있어도 *"없다"* 는 말할 수 없다.
2. 원룸은 **벽이 얇아 옆집 소리 · 층간 소음 · 켜둔 TV**가 섞인다 — 빈집에서도 '사람 소리'가 난다. 소리 단독 재실 판단은 오검출에 취약하다.
3. **항상 나오는 사람의 주파수는 호흡(0.2–0.33 Hz)이다.** 이것은 공기 진동이 아니라 **가슴의 미세한 움직임**이라 마이크가 아니라 **레이더로 본다.**
   LD2410의 '정지 인체 감지'가 바로 이 미세동작 에너지를 쓰는 것이다. **즉 피드백 ②의 직관은 mmWave가 이미 구현하고 있다.**
4. 소리는 **행동 분류**(샤워 · 요리 · 청소)에서 가치가 있다 — 검증된 연구가 있다(Comai 2025: 마이크 1개 + ESP32, 물소리 4종 90.6 %).
   단 **Isaac Sim에는 음향 센서가 없어** 시뮬레이션에서는 분류기 자체를 검증할 수 없다. → **확장 신호로 인터페이스만 예약**한다(§1.4).

### 1.4 소리 신호 — 확장 슬롯으로 예약

## 2. 가상 센서 — 측정하지 않고 계산한다

### 2.1 CO₂ — 측정도 계산도 하지 않고 환기량으로 보장한다 (v1.5 개정 · 2026-10-06)

| 버전 | 방식 | 문제 |
|---|---|---|
| v3.0 | NDIR 실측 (22,000원) | 피드백 ① — 다른 상태로 판단할 수 있는가 |
| v3.1 | 가상 CO₂ = 재실 × 1인 발생량 − 환기량 | **사람 수를 모른다**(레이더는 있음/없음만) · 가스 연소 · 활동량 · 반려동물 누락 · 검증이 같은 식끼리 비교라 순환 |
| **v3.4** | **재실 기본 환기 + 상황 이벤트** | 사람 수 · CO₂ 값 모두 필요 없음 |

CO₂를 보는 목적은 하나 — **사람 수에 비해 환기가 충분한가**다. 그렇다면 값을 재거나 추정하지 말고 **필요한 환기량을 처음부터 공급**하면 된다(아파트 전열교환기 상시 운전과 같은 방식).

| 층 | 조건 | 동작 |
|---|---|---|
| **기본** | 재실 (문 + 레이더) | 1인 기준 기본 환기 — 일반 25 · 공부 40 · 수면 16 m³/h ([`07` §3.3](07_modes_rules_events.md)) |
| **상황** | 요리 E1 · 샤워 E3 · 빨래 E10 | 원인별 배기 · 급기 · 제습 — 창문 · 흡기가 막혀도 회복 ([`07` §3.5](07_modes_rules_events.md)) |
| **미달** | 필터 막힘 · 팬 고장 · 소음 상한 | E4 → 다른 수단 · 소음 1단계 완화 · 알림 |

- 정상상태 참값 CO₂ (1인 · 틈새 0.15회/h): 일반 약 1,000 · 공부 약 800 · 수면 약 1,000 ppm
- 사람 수를 세지 않는 대가: 손님 2명이면 일반 모드 약 1,550 ppm → 한계 #16
- CO₂는 **시뮬레이션 참값으로만** 계산해 기본 환기량이 충분했는지 검증한다(지표 #9 · EXP-3). 제어기는 CO₂를 구독하지 않는다
- 피드백 ①에 대한 답: *"CO₂ 센서를 계산으로 바꿨다"* 가 아니라 **"CO₂를 볼 필요가 없게 환기를 설계했다"**

#### 비 오면 배기를 멈췄던 이유 — 그리고 바꾼 기준

배기팬을 돌리면 뺀 만큼 바깥 공기가 틈새 · 급기로 들어온다. 여름 장맛비에는 바깥 공기의 **절대습도가 실내보다 높아**(외기 24 °C · 95 % ≈ 18 g/kg, 냉방 중 실내 26 °C · 55 % ≈ 11.7 g/kg) 배기할수록 습기를 들인다. 그래서 C1 · `09`는 "비 → 배기 정지"로 적었다.
하지만 비는 **"바깥이 더 습하다"의 대리 지표**였을 뿐이다.

| 상황 | 실내 이슬점 | 바깥 이슬점 | 배기 |
|---|---:|---:|---|
| 장맛비 · 냉방 중 | 약 16 °C | 약 23 °C | ✗ 습기 유입 |
| 장맛비 · **샤워 직후** | 약 24–25 °C (일시) | 약 23 °C | ✅ 차이가 있는 동안만 |
| 겨울비 | 약 9 °C | 약 4 °C | ✅ 환기가 곧 제습 (난방 손실 때문에 짧게) |

→ **규칙 I10:** 배기 · 창문으로 제습하는 것은 *바깥 이슬점 < 실내 이슬점 − 2 °C* 일 때만, 차이 < 1 °C면 중단. 이미 계산하는 이슬점(결로 여유)과 기상청 외기 온습도로 판정하므로 **센서 추가 없음.** 기본 환기는 예외(건강 최소량).

### 2.2 가상 조도 — 페일세이프로만 채택

팀원 안은 조도 센서(BH1750)를 빼고 태양 위치 · 구름 · 블라인드 각도로 계산하자고 했다(Xie & Sawyer 2021 — 검증됨).
**기본 센서로는 기각, 페일세이프로 채택**한다.

| 기각 이유 | 내용 |
|---|---|
| 원룸 환경 | 인접 건물 그림자 · 좁은 동 간격으로 **창마다 일사가 크게 다르다.** 해당 연구는 사전 시뮬레이션한 사무실 모델이 필요 — 원룸마다 만들 수 없다 |
| 비용 대비 | BH1750은 2,000원. 빼서 얻는 절감보다 잃는 정확도가 크다 |

| 채택 방식 | 내용 |
|---|---|
| X3 센서 고장 | BH1750 무효 시 **가상 조도로 전환** (기존: 조명 정책 동결 → **v3.1: 가상값으로 계속 제어**) |
| 교차 확인 | 실측과 가상값 차이가 크게 지속되면 센서 가림 · 오염 경고 |

### 2.3 요리 감지 — 후드 아래 온도 + 미세먼지 + 쿡탑 전력 (v1.4 개정)

> **v1.4 결정 (2026-10-06):** 미세먼지 센서는 **유지**하고, **후드 아래 온도 센서**(DS18B20 방수형 · ~2,000원)를 더해 서로 보완한다.
> 이유: 원룸에는 공기청정기가 없거나 **내장 센서가 없는 저가형**이 많아, 실내 공기 상태를 아는 수단이 미세먼지 센서뿐인 경우가 많다.

| | v1.1 | **v1.4** |
|---|---|---|
| 요리 시작 | 쿡탑 전력 (플러그형만) · 가스는 미세먼지 잔차 (연기가 나야 앎) | **후드 아래 온도 상승** (가스 · 빌트인 · 인덕션 모두) ∨ 쿡탑 전력 (플러그형) — **켜는 즉시** |
| 요리 끝 | 미세먼지가 기준으로 돌아옴 (느림) | **후드 아래 온도 하강** · 쿡탑 전력 꺼짐 (빠름) |
| 미세먼지의 역할 | 요리 감지 | **연기 세기 · 원인 구분 · 실내 공기 상태** |

**후드 아래 온도 센서** — 레인지 바로 위 후드 하단에 붙인다. 조리 열기는 위로 올라와 후드 아래에 고이므로 **불꽃 색 · 레인지 종류와 상관없이** 온도가 빠르게 오른다.
시판 열 감지 레인지후드(서미스터 · 적외선 센서)와 같은 원리다.

```text
요리 시작 = (후드 아래 온도 − 실내 온도 ≥ 8 °C  AND  상승 ≥ 3 °C/분)  OR  쿡탑 전력 가동(플러그형)
요리 끝   = 후드 아래 온도가 실내 + 3 °C 이내로 내려옴  AND  쿡탑 전력 꺼짐 → 후드 5분 잔류 운전
```

#### 두 센서를 합치면 미세먼지의 원인을 가를 수 있다

| 후드 아래 온도 | 실내 미세먼지 | 판단 | 동작 |
|:---:|:---:|---|---|
| ↑ | ↑ | **요리 (연기)** | 후드 + 보충 급기 + 청정기 |
| ↑ | – | **물 끓이기 · 수증기만** | 후드 약 · 청정기 그대로 |
| – | ↑ · 가습기 켜짐 · 습도 상승 | **초음파 가습기 물방울** (수돗물 미네랄) | **후드 끔** · 청정기 약 · 가습기 교체 · 정수 사용 안내 |
| – | ↑ · 외기 PM도 높음 (모델 잔차 ≈ 0) | **바깥 공기 유입** | 창문 닫기 · 필터 흡기 · 청정기 |
| – | ↑ · 그 외 | **원인 미상** (열 없음) — 원인을 추정하지 않는다 | 청정기 · 환기 · **후드 끔** |

> **후드는 "열 + 연기"일 때만 켠다.** 미세먼지 센서만 있으면 열 없는 미세먼지(가습기 물방울 등)에도 후드를 켜게 되고, 후드의 음압이 오염된 바깥 공기까지 끌어들인다.
> 피드백 ①의 *"서로 다른 신호 2개 이상으로 판단하라"* 가 여기서도 그대로 적용된다.

#### 덤 — 불을 켠 채 외출 경고 (이벤트 E15)

문 기반 재실 판정이 **빈방**인데 후드 아래 온도가 높거나 쿡탑 전력이 가동 중이면 **즉시 사용자에게 알린다.**
플러그형 인덕션은 계량 플러그로 **전원을 차단**할 수 있다. 가스레인지는 경고만 한다(가스 차단기 연동은 확장).
시판 화재 예방 장치(iGuardStove · Safera Sense)와 같은 목적이다.

#### 시뮬레이션 모델

```text
후드 아래 온도 : T_hood = T_room + ΔT_plume,   τ·dΔT/dt = k·H_cook − ΔT     (τ ≈ 20 s, H_cook = 조리 열 W)
초음파 가습기  : PM 발생 S_hum = 가습량 × 수돗물 미네랄 농도 (시나리오 파라미터, 가열식 · 임펠러식은 0 · 1/3)
```

## 3. 전력 기반 기기 상태 판정 (피드백 ③)

### 3.1 원칙

- 명령을 보냈다고 **"켜졌다"고 가정하지 않는다.** 실제 전력으로 상태를 판정한다.
- 상태가 **바뀌는 순간(엣지)** 을 이벤트로 발행한다.
- 명령 없이 상태가 바뀌면 **사용자가 직접 조작**한 것이다.

### 3.2 측정 수단 — 두 가지 중 선택 (시뮬레이션에서는 동일)

| | **A. CT 클램프 (팀원 안)** | **B. 계량 스마트 플러그 (제안)** |
|---|---|---|
| 구성 | SCT-013 + ADS1115 + 바이어스 회로 + **라인 분리 어댑터** | KC 인증 전력 계량 플러그 (W 단위 직접 출력) |
| 측정 | Irms → 전력 추정 (역률 가정) | 유효전력 직접 |
| 제어 | ❌ 측정 전용 | ✅ **ON/OFF 겸용** — 릴레이 대체 |
| 220 V 안전 | ⚠️ 상선 분리 어댑터 제작 시 노출 위험 | ✅ 배선 노출 없음 |
| 비용 | 채널당 ~8,000원 + ADC 공유 | 개당 ~15,000원 |
| 적합 | 측정만 필요한 고전력 기기 (교육용) | **실물 구현 권장** |

> **B를 권장하는 결정적 이유:** v3.0에서 *"릴레이 모듈을 220 V에 직결하면 안 된다"* 는 한계(#14)가 있었다.
> 계량 플러그는 **제어와 측정을 한 번에, 안전하게** 해결한다. 제습기 · 가습기는 플러그로 켜고 끄면서 동시에 상태를 안다.
> **시뮬레이션에서는 두 방식 모두 `기기별 전력 신호`로 추상화**되므로 실험 결과에는 영향이 없다.

### 3.3 측정 대상 5개 — "판단에 쓰이는 기기"만

| 기기 | 측정 이유 | 제어 |
|---|---|---|
| **에어컨** | IR 확인 · 써모오프 · 에너지 · 셋백 실험 | IR (측정만) |
| **제습기** | 상태 확인 · **물통 가득 감지** | 플러그 ON/OFF |
| **가습기** | 상태 확인 · 물 부족 감지 | 플러그 ON/OFF |
| **쿡탑 (전기레인지 · 인덕션)** | **요리 선제 감지** · 전력 한도 | 측정만 |
| **세탁기** | **빨래 건조 시작 감지** (탈수 종료) | 측정만 |
| (선택) PC | AUTO 모드의 공부 판정 보조 | 측정만 |

> 빌트인 직결 기기(레인지후드 · 실링팬)는 **측정하지 않는다** — 벽 배선을 건드려야 하기 때문이다(임대 원룸).

### 3.4 다단계 상태 머신

| 기기 | 상태 | 판정 기준 (예시 · 실측 교정) | 의미 |
|---|---|---|---|
| 에어컨 | OFF | < 10 W | |
| | **송풍 (써모오프)** | 20–100 W | **설정온도 도달** — 압축기 정지, 팬만 가동. OFF로 오판 금지 |
| | 가동 | > 250 W | 압축기 운전 |
| 제습기 | OFF / 대기 / 가동 | < 3 W / 3–30 W / > 120 W | **명령 ON인데 '대기' 지속 + 습도 높음 → 물통 가득 추정** |
| 쿡탑 | OFF / 가열 | < 20 W / > 300 W | 가열 진입 = 요리 시작 |
| 세탁기 | OFF / 세탁 / **탈수 → 종료** | 패턴 | **종료 엣지 = 빨래 건조 시작 후보** |

**확정 규칙:** 진입은 3 s, OFF 확정은 10 s 지속 — 기동 돌입전류 · 노이즈에 반응하지 않는다. (팀원 `idea2.md` §1.6 상태 머신 코드를 그대로 채택)

### 3.5 명령 ↔ 실측 비교 — IR 확인이 5분 → 10초로

| 명령 | 실측 | 판정 | 동작 |
|---|---|---|---|
| ON 전송 | 10 s 내 가동/송풍 진입 | ✅ 정상 | – |
| ON 전송 | 10 s 내 변화 없음 | ❌ 수신 실패 | 재송신 (최대 2회) → E9 |
| 명령 없음 | 상태 변화 | **수동 조작** | **E12** — 30분 자동 제어 보류 · 목표 오프셋 학습 |

**v3.0과의 관계:** v3.0의 *"효과로 역확인(5분 내 −0.3 °C)"* 은 **2차 확인으로 남긴다.**
전력은 *"켜졌는가"* 를, 환경 변화는 *"제대로 일하는가"* 를 본다 — 둘이 다르면 **효율 저하(필터 막힘 · 냉매 부족) 추정**으로 이어진다.
(Niknami 외 2024: 증발기 오염 시 냉방 능력 저하 — 검증됨)

### 3.6 수동 조작 존중 (규칙 I9)

| 사용자 행동 | 시스템 해석 | 동작 |
|---|---|---|
| 에어컨을 직접 켬 | *"덥다"* | 30분간 에어컨 자동 제어 보류 · **창문 닫기 · 배기 낮춤**은 계속 (협조) |
| 에어컨 설정을 직접 낮춤 | *"목표가 높다"* | 해당 모드 냉방 목표에 **−0.5 °C 오프셋 누적** (상한 ±1.5 °C) |
| 제습기를 직접 끔 | *"시끄럽다 / 필요 없다"* | 30분 보류 · 같은 시간대 반복 시 해당 모드 소음 등급 하향 제안 |

> 사용자를 이기려 하지 않는다. **수동 조작은 고장이 아니라 사용자 의도에 대한 정보**다.

## 4. 우선 목표와 허용 손실 예산 (피드백 ④)

### 4.1 문제

v3.0 규칙 I6은 *"여름 제습은 에어컨, 제습기는 발열 때문에 쓰지 않는다"* 였다. **쾌적이 목표일 때는 맞다.**
그러나 **빨래 건조처럼 '빨리 말리는 것'이 최우선일 때**는 사람들이 실제로 **에어컨과 제습기를 함께 켠다.** 제습기의 열은
에어컨이 치우고, 제습기는 습도를 끝까지 끌어내린다. **온도를 조금 손해 보더라도 건조 시간을 줄이는 선택**이다.

### 4.2 설계 — 이벤트가 '우선 목표'와 '감수할 손실의 상한'을 선언한다

```yaml
# 이벤트 E10 (빨래 건조) 의 선언 예
primary_goal: drying_time              # 최우선 목표
budget:                                # 이 범위 안의 손실은 감수한다
  indoor_temp_rise_c: 1.0              #   재실 시 실내 온도 +1.0 °C 까지 (외출 중 3.0)
  noise_grade: N2                      #   소음은 보통까지
  extra_energy_wh: null                #   에너지 증가 허용 (상한 없음 — 단 누진 방어 중이면 제한)
overrides: [I6]                        # 해제하는 규칙 — 계절별 제습 수단 규칙
never_overrides: [L0, L1, L2]          # 안전 · 건강 · 결로는 절대 해제 불가
```

| 동작 | 설명 |
|---|---|
| 예산 안 | 우선 목표를 위한 명령이 다른 쾌적 목표를 해쳐도 허용 (예: 제습기 + 에어컨 동시) |
| 예산 초과 예상 | **30분 앞 예측**으로 예산을 넘을 것 같으면 우선 목표 동작을 **한 단계 낮춘다** (예: 실링팬 강 → 약 대신 에어컨 설정 −1 °C) |
| 예산 고정 항목 | 안전 · 건강 · 결로(L0–L2)는 예산 대상이 아니다 — 빨래를 말리려고 결로를 감수하지 않는다 |

### 4.3 빨래 건조 이벤트 (E10)

| 항목 | 내용 |
|---|---|
| 진입 | ① 세탁기 **탈수 종료 엣지** + 30분 내 실내 RH 상승 ≥ +3 %p/h 가 1시간 지속 + 요리 · 샤워 신호 없음 / ② 사용자 선언 `/studio/cmd/activity = "LAUNDRY"` |
| 동작 | 제습기 ON · **에어컨 냉방으로 제습기 열 상쇄**(I6 해제) · 실링팬 정 강(빨래에 기류) · 창문은 외기 절대습도가 낮을 때만 |
| 해제 | 건조 모델 잔여 수분 ≤ 5 % 또는 RH 상승률 ≈ 0 이 30분 지속 또는 최대 8시간 |
| 외출 중 | 온도 예산 3.0 °C로 완화 · 에어컨 생략 가능 → **에너지 절약형 건조** |

**건조 모델** (환경 모델 추가)

```text
E_laundry = k_l · A · (w_sat(T) − w) · (1 + c_v · v_air)      [g/h]   — 포화 수증기 부족분(VPD)에 비례
초기 수분 M₀ = 2.0 kg (1인 세탁 1회, 탈수 후) · k_l 은 '24 °C · 60 % · 무풍 → 10시간 건조'로 교정
```

> **이 식이 피드백 ④의 직관을 정량화한다.** 제습기는 습도(w)를 낮추고 **온도(T)를 올려 w_sat을 키우므로 두 방향 모두 건조를 빠르게** 한다.
> 그래서 열은 '부작용'이면서 동시에 건조에는 '이득'이다 — 에어컨은 사람이 견딜 만큼만 그 열을 덜어 준다.

### 4.4 모델 정정 — 제습기 발열

v3.0 문서는 제습기 발열을 *"+200 W"* 로 적었다. **실제로는 전력 + 응축 잠열이다.**

```text
H_dehum = P_elec + R_dehum · h_fg  = 200 W + 417 g/h × 0.68 Wh/g ≈ 480 W
```

**발열이 2배 이상 크다.** C13(장마철 제습)의 *"여름엔 제습기를 쓰지 않는다"* 결론이 더 강해지고,
C15(빨래 건조)에서 *"에어컨이 덜어 줘야 할 열"* 이 왜 큰지 설명된다.

## 5. 에너지 소비 패턴 분석과 예측 (피드백 ⑤)

### 5.1 설계 원칙 — "에너지 분석"을 세 질문으로 나누고, 질문마다 맞는 모델을 쓴다

> 피드백 ⑤는 *"LSTM 같은 AI 모델로 소비 패턴을 분석할 수 있다"* 고 **예시**했다. 예시를 그대로 따르기보다 **이 프로젝트의 조건에 가장 맞는 모델**을 고른다.
> 조건은 셋이다 — ① **데이터가 적다**(1인 원룸 · 수 주) ② **하지 않은 전략의 에너지도 계산해야 한다**(셋백 vs 끄기) ③ **불확실성이 필요하다**(귀가가 언제일지 분포).

| 질문 | 모델 | 성격 | 왜 이 모델인가 |
|---|---|---|---|
| **① 어떤 전략이 덜 쓰나?** (셋백 vs 끄기 · 프리쿨링 시점) | **회색상자 2R2C 열모델 — 데이터로 R · C 식별** | 물리 + 데이터 | 전략을 바꿔 넣고 에너지를 **계산**한다(반사실 예측). 파라미터 6–8개라 **1–2주 데이터로 식별** 가능 |
| **② 언제 돌아오나?** (귀가 · 외출 시간) | **분위수 회귀 (LightGBM quantile)** · 기준선: 요일별 경험 분포 | 머신러닝 | **분포(10/20/50/80분위)가 바로 나온다.** 수 주 데이터로 동작 · 특성 중요도로 설명 가능 |
| **③ 얼마나 쓰고 있나?** (일 · 월 kWh · 이상 감지 · 누진) | **변화점 회귀 (냉방도일 회귀)** | 통계 | 건물 에너지 기준선의 표준 방법. 파라미터 2–3개(기준온도 · °C당 kWh)라 **바로 해석**된다. 잔차가 곧 **이상 감지** 신호 |
| (데이터 생성) | **비균질 마르코프 재실 모델** | 확률 모델 | 페르소나 일정을 **시간대별 전이확률**로 생성 — 임의 규칙보다 현실적인 불규칙성 |

### 5.2 LSTM을 쓰지 않는 이유 (검토 후 제외)

| 조건 | LSTM | 선택한 모델 |
|---|---|---|
| 데이터량 (1인 원룸 · 수 주 ≈ 시간 단위 수천 점) | 보통 수개월 데이터에서 단순 모델을 앞선다 | 수 주로 동작 |
| **반사실 예측** — 하지 않은 전략의 에너지 | ❌ 관측한 패턴만 재현 | ✅ 회색상자 모델은 전략을 바꿔 계산 |
| 불확실성 (귀가 분포) | 별도 설계 필요 | ✅ 분위수 회귀가 직접 출력 |
| 설명 가능성 (발표 · 사용자) | 낮음 | ✅ R · C · 기준온도 · 특성 중요도 |
| 합성 데이터 평가 | 생성 규칙을 학습할 뿐 | (모든 모델 공통 한계 — §5.8) |

> **"AI 모델"은 데이터가 답을 정하는 곳(귀가 예측)에 쓰고, 물리가 답을 정하는 곳(전략 비교)에는 물리 모델을 쓴다.**
>
> **v1.6 (논문용):** 제어기 설계는 그대로 두고, 이 판단이 맞는지를 **LSTM · 심층 강화학습과 같은 조건에서 비교하는 실험(EXP-5)** 으로 검증한다 — 계획 · 문헌: [`10`](10_energy_control_comparison_study.md) · [`05` §4.9](05_related_work.md)
> 원룸 벽걸이 에어컨에도 회색상자 에너지 모델을 보정 · 검증한 연구가 있다(OSTI 2418657).

### 5.3 기대비용 최소화 프리쿨링 — 분위수 규칙을 넘어서

```text
귀가 분포  →  표본 100개 (분위수 회귀로 생성)
후보 시작 시각  t ∈ {지금, +5분, … , 귀가 90분위} (5분 격자)
각 t 에 대해  회색상자 모델로 시뮬레이션:
    비용(t) = E[에너지(t)] + λ · E[귀가 후 불쾌 시간(t)]
선택  t* = argmin 비용(t)                    λ : 모드별 쾌적 가중치 (user_modes.yaml)
```

- *"20분위에 맞춘다"* 같은 고정 규칙은 **λ가 특정 값일 때의 근사해**다. 기대비용을 직접 최소화하면 **귀가 분포가 넓은 날은 일찍, 좁은 날은 늦게** 자동으로 맞춘다.
- 후보 20여 개 × 표본 100개 × 2R2C 적분 — 1분 주기로 충분히 계산된다.
- 같은 틀에서 **셋백 / 끄기 / 끄기 + 프리쿨링** 세 전략의 기대비용을 비교하면 §5.4의 T\* 판단도 실시간으로 나온다.
- 고정 20분위 규칙은 **예측이 불확실할 때(데이터 부족 초기)의 폴백**으로 남긴다.

### 5.3-1 제어용 모델 ≠ 참값 모델 — 순환 논증을 피한다

시뮬레이션의 환경 모델이 2R2C인데 제어기도 2R2C를 쓰면 **"자기 답을 자기가 맞히는"** 실험이 된다. 그래서 둘을 분리한다.

| | 참값(환경) 모델 | 제어용 모델 |
|---|---|---|
| 구조 | **3R3C** — 공기 · 가구/침구 · 외피 3노드 + 일사 변동 + 측정 노이즈 | **2R2C** |
| 파라미터 | 고정 (W08 문헌값) | **기록 데이터로 식별** (1주 · 2주 · 4주) |
| 검증 | – | **EXP-4**: 학습 기간별 온도 예측 RMSE · T\* 오차 → *"데이터 몇 주면 충분한가"* |

### 5.4 셋백 vs 끄기 — 손익분기 외출 시간 T\* (팀원 `idea2.md` 가설 채택)

**가설:** 인버터 에어컨은 짧은 외출이면 **설정온도를 올려 켜 두기(셋백)**, 긴 외출이면 **끄고 귀가 전 프리쿨링**이 유리하다.

| 근거 | 내용 | 검증 |
|---|---|:---:|
| 다이킨 (2016 여름, 오사카) | 낮 35분 · 밤 18분 이내 외출이면 켜 두기가 유리 | ✅ |
| Niknami 외 (Energy and Buildings, 2024) | 설정 1 °C 상향 시 약 57 W · 연 279 kWh 감소 | ✅ |
| MPC 실험 (2022) | 적응형 MPC가 24 °C 연속 운전 대비 7.06 % 이상 절감 | ✅ (팀원 문서의 "on/off 20.12 % 추가 소비"는 **원문 확인 필요**) |

**시뮬레이션으로 T\* 표를 만든다 — 이것이 프로젝트의 기여 지점**

| 실험 EXP-1 | 값 |
|---|---|
| 외출 시간 | 0.5 / 1 / 2 / 4 / 8 h |
| 외기온 | 28 / 32 / 35 °C |
| 전략 | ① 끄기 → 귀가 후 켬 ② 셋백 +2 °C 유지 ③ 끄기 + 기대비용 최소화 프리쿨링 |
| 실행 | 5 × 3 × 3 = **45회 (고속 모드, 약 1.5시간)** |
| 산출 | 외기온별 **T\*** · kWh · 귀가 후 쾌적 회복 시간 · 귀가 시 습도 · **식별 모델의 T\* 오차**(EXP-4와 연계) |

> ⚠️ **이 실험이 의미를 가지려면 환경 모델에 두 가지가 있어야 한다.** 없으면 결과는 모델이 정한 답일 뿐이다.
> ① **벽체 · 가구 열용량** (2R2C 모델, §6.1) — 끄는 동안 축열되고 재가동 시 그 열까지 빼야 한다
> ② **인버터 부분부하 효율 곡선** — 저출력 연속 운전이 고출력 재가동보다 효율이 좋은 이유

**제어 규칙 (EXP-1 결과로 확정)**

| 조건 | 동작 |
|---|---|
| 예상 외출 < T\*(외기온) | 셋백 +2 °C 유지 |
| 예상 외출 ≥ T\*(외기온) | 끄기 → §5.3 기대비용 최소화 프리쿨링 |

> 운영 중에는 고정 표 대신 §5.3의 기대비용 비교로 판단하고, **EXP-1의 T\* 표는 그 판단이 맞는지 검증하는 기준**이 된다.
| 수면 중 | 끄지 않음 — 설정 유지 + 실링팬 약 |

### 5.5 전력 한도 (규칙 I8) — 원룸에서 실제로 일어나는 문제

원룸은 계약전력 · 차단기 용량이 작다. **인덕션(2 kW) + 에어컨(0.9 kW) + 제습기(0.2 kW) + 후드**를 동시에 쓰면 한도에 닿는다.

| 항목 | 값 |
|---|---|
| 한도 | `power_limit_w` = **3,000 W (가정 A17 · 원룸마다 다름 — 설정값)** |
| 진입 | 총 전력 ≥ 한도의 90 % (이벤트 E11) |
| 차단 순서 (미뤄도 되는 것부터) | 가습기 → 제습기 → 청정기 단 하향 → 에어컨 설정 +1 °C → 에어컨 풍량 약 |
| **절대 끄지 않음** | **요리 중 후드** (건강 L2) · 창문 안전 · 센서 |
| 복원 | 한도의 75 % 미만 5분 지속 시 역순 복원 |

### 5.6 누진 구간 방어 (선택 · 기본 비활성)

주택용 전기요금 하계(7–8월) 누진 구간은 **300 kWh / 450 kWh** 경계에서 단가가 크게 오른다(1단계 120원 → 2단계 214.6원 → 3단계 307.3원/kWh — 검증됨).

|---|---|
| 판단 | 이달 누적 + 남은 일수 × 예측 일소비 > 구간 경계 |
| 동작 | 수면 외 모드의 냉방 목표 +0.5 °C · 사다리에서 실링팬 칸 우선 · 사용자 알림 |
| 기본값 | **비활성** — 사용자가 켜는 옵션 (`user_modes.yaml`) |

## 6. 환경 모델 추가

### 6.1 열모델 — 참값 3R3C / 제어용 2R2C (v3.0 1R1C → 교체)

```text
C_air · dT/dt   = (T_m − T)/R_im + (T_out − T)/R_ve + H_internal + H_solar,air − Q_ac
C_m   · dT_m/dt = (T − T_m)/R_im + (T_out − T_m)/R_wall + H_solar,mass
  T_m : 벽체 · 가구 · 침구 등 축열 질량의 온도
```

### 6.2 인버터 에어컨 전력

```text
P_elec = Q_cool / COP(PLR, T_out)        PLR = Q_cool / Q_rated
COP(PLR) : PLR 0.3–0.5 에서 최대, 0.2 미만은 단속 운전으로 급감, 1.0 에서 정격
```

### 6.3 기기 전력 프로파일 (가상 전력 신호)

| 기기 | 프로파일 |
|---|---|
| 에어컨 | 기동 돌입 → 가동(P_elec) → 설정 도달 시 송풍 20–100 W 반복 |
| 제습기 | 가동 200 W · 대기 10 W · 물통 가득 시 대기로 급감 |
| 쿡탑 | 가열 단계별 500–2,000 W · 인덕션 펄스 |
| 세탁기 | 세탁 → 헹굼 → **탈수 고전력 구간 → 종료** |
| 공통 | 측정 노이즈 ±3 % · 10 s 이동평균 |
